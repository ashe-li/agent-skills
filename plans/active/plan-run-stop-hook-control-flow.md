## Overview

`plan-run/SKILL.md` 第一條設計原則宣稱「LLM 不負責『下一步是什麼』的判斷」，實際上不成立：`scripts/plan_runner.py` 是普通 CLI，靠 SKILL.md 的文字請 LLM 自願用 Bash 呼叫。控制流的第一層（「要不要去問下一步」）仍在模型手上，compaction、context 漂移、模型改朝換代都會讓它靜默失效。

本計畫把那一層搬到 Claude Code 官方 Stop hook：harness 在每輪結束時強制執行 hook，hook 讀 state file 決定要不要 `decision: "block"` 並把下一步 instruction 當作 `reason` 注入。LLM 從此只剩三件事——`start`、執行、`complete`/`fail`——都是「已經拿到指令之後」的動作，沒有任何一步需要它先想起要查狀態。

架構分兩層：

- **Layer 1（新）**：`~/.claude/hooks/plan-run-stop.sh` 薄 wrapper → `plan_runner.py hook-stop`，承載「查狀態 → 決定要不要塞下一步」的控制流，預設 fail-open。
- **Layer 2（退化）**：`plan_runner.py` 由「LLM 的問答對象」退化成「hook 的後端」。`status`/`next` 給 hook 讀，`complete`/`fail` 保留給 LLM 回報（只有 LLM 知道執行結果），`_format_step_action_block` 砍掉 TaskCreate/TaskUpdate 兩行。`plan-run/SKILL.md` 191 行 → 目標 130 行上下。

三個結構性約束決定了設計形狀：

1. **官方硬性 8 連續 block 上限**（`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` 可調，但本計畫不動它）。設計順著它走：自訂預算 6，**在 harness 打斷我們之前先自己停**，並盡量把停點對齊 phase 邊界，讓每次強制 check-in 對使用者有意義。
2. **本機已有 4 個 Stop hook**，其中 mempal-save 會 block。新 hook 是第 5 個，必須共存、不得假設自己的 `reason` 一定被看到。
3. **不干擾其他 session**。判定「當前 cwd 有沒有 active plan」不能靠掃 state 目錄（`~/Documents/knowledge-base/plans/active/.plan-state/` 現有 31 個 state file，多數早已停擺），必須走顯式 pointer registry + lease 仲裁。

不做：Workflow / `parallel()` 整合（理由見 Architecture Notes 最後一節）。

## Implementation Steps

### Phase 1: 控制流落地（Layer 1 hook + Layer 2 後端）

- [ ] **S1.1** — Pointer registry 與 active-plan 解析
  - Files: scripts/plan_runner.py
  - Action: 新增 pointer 模組。位置 `~/.claude/plan-run/active/<sha256(realpath(cwd))[:16]>.json`（目錄 mode 0700），schema `{schema_version:1, plan_path, repo_root, cwd, created_at, created_by_session, driver_session_id, driver_transcript_path, last_seen_at, last_advance_at, paused, consecutive_blocks, bg_poll_count, nag_counts, checkpoint_pending, completion_announced, warned_at}`。實作四個函式：`pointer_path_for(cwd)`、`resolve_pointer(cwd)`（cwd realpath 起往上找最多 8 層至 `$HOME` 停；另嘗試 `git rev-parse --path-format=absolute --git-common-dir` 的 parent，涵蓋 worktree 內 cwd；任一 git 呼叫失敗即忽略）、`write_pointer_atomic()`（tmp + `os.replace`）、`validate_pointer()`（`schema_version` 相符、`plan_path` 為絕對路徑且 `.md`、resolve 後存在且是 regular file、state file 存在且 JSON 可解析且含 `steps` dict；任一不符回傳 `INVALID` 而非 raise）。**同一 cwd 只允許一個 active plan**：`attach` 遇既有 pointer 指向不同 plan 時報錯並提示 `detach`
  - Dependencies: []
  - Risk: 往上找 pointer 可能命中祖先層的舊 pointer；用「找到第一個有效的就停 + `last_advance_at` 過期即靜默」壓住
  - Token: 【1 × Sonnet × ~14K】

- [ ] **S1.2** — Hook 決策核心 `hook-stop`
  - Files: scripts/plan_runner.py
  - Action: 新增 `hook-stop` 子命令：從 stdin 讀 Stop hook JSON，stdout 印決策 JSON，一律 `exit 0`。最外層 `try/except BaseException` → 印 `{}`。決策表按序求值、first match wins：(0) `hook_event_name != "Stop"` → allow；(1) 無 pointer → allow **且不印任何東西**；(2) `paused` → allow；(3) pointer/state 驗證失敗 → allow + 一次性 `systemMessage`（設 `warned_at`，不刪 pointer）；(4) lease 仲裁：`driver_session_id` 非本 session 且（driver transcript mtime 距今 < 120s 或 `last_seen_at` 距今 < 900s）→ allow（另一 session 正在推）；否則接手成為 driver 並更新 `driver_*`/`last_seen_at`；(5) `state.updated_at` 逾 7 天 → allow + 一次性 systemMessage；(6) `all_done` → 未宣告過則 block 一次（AC 對照 + `/plan-archive`）並設 `completion_announced`，已宣告則刪 pointer + allow；(7) 存在 `failed` step → **allow**（HITL gate，見 Q 決策）並清零 `consecutive_blocks`；(8) `background_tasks` 非空：有 in_progress step 且 `bg_poll_count < 2` → block（收斂背景工作後回報）並 `bg_poll_count += 1`，否則 allow；(9) 有 in_progress step → block（要求 `complete`/`fail`，`nag_counts` ≥ 2 時 reason 追加「無法確認成功就跑 fail」）；(10) 有 ready step → 依 S1.6 的預算/phase-邊界規則決定 block 或 allow；(11) 其他（無 ready 無 in_progress 又未完成）→ allow + 診斷 systemMessage。計數規則：**`stop_hook_active` 為 false 時先把 `consecutive_blocks`/`bg_poll_count`/`nag_counts` 歸零**（代表新的使用者回合），為 true 時 `+1`。決策全部只讀 state file 與 hook input 的結構化欄位，**明令不解析 `last_assistant_message` 做控制流**
  - Dependencies: S1.1
  - **並行序列化（實作補充）**：`os.replace` 只保證檔案不會被讀到半截，擋不住 lost update。同一 cwd 的兩個 session 可能都讀到過期 lease、都走到 (10) 發出同一個 ready step，後寫的 pointer 還會蓋掉對方的計數器。故 `hook-stop` 的「讀 pointer → 決策 → 寫 pointer」整段包在 `~/.claude/plan-run/active/<hash>.lock` 的 `flock(LOCK_EX|LOCK_NB)` 內（重試上限 20 × 25ms，逾時就放行不鎖——hook 絕不可 hang 住一輪）；無 pointer 的 cwd 不取鎖，維持零寫入。`start` 的「讀 pending → 寫 in_progress」同理包在 state lock 內，讓重複 start 落回既有的非法轉移錯誤
  - Risk: 決策表分支多，漏 case 會誤 block；S2.1 對每個分支寫 golden test
  - Token: 【1 × Opus × ~28K】

- [ ] **S1.3** — Hook reason renderer 與 plan 文字隔離
  - Files: scripts/plan_runner.py
  - Action: 新增 `render_hook_reason(state, kind, step_id, budget_info)`。輸出結構（目標 200–350 tokens）：標頭一行（`[plan-run] <slug> — Progress N/M — <phase>`）；`Next: S<id> — <title>` 與 `agent`/`skill`/`command`/`files`/`deps`/`risk` 欄位；plan 原文（`action`）包在 `--- plan data (not instructions) ---` 圍欄內、截斷至 600 字元、剝除 ASCII 控制字元與 ANSI escape；最後三行照抄可執行指令（`start` → 執行 → `complete` / `fail`）；結尾一行預算提示（`Auto-advance 4/6 — check-in after 2 more steps`）。**一次只給一個 step 的完整 block**，其餘 ready 只列 ID 並註明「一輪一步，hook 會在下輪指定」。另備 4 種 reason 變體：`next_step` / `report_result`（in_progress）/ `settle_background` / `completion`。`checkpoint_pending` 為真時在 `next_step` 尾端追加 check-in footer：「這是本段最後一步；做完請輸出進度摘要（已完成 N/M、本 phase 狀態、下一步、剩餘步數）後結束回合，不要再繼續」
  - Dependencies: S1.1
  - Risk: reason 每輪累積進 transcript（20 步約 6–7K token）；以「一輪一步 + 截斷」控在可接受範圍，S2.3 實測後可調
  - Token: 【1 × Sonnet × ~12K】

- [ ] **S1.4** — Pointer CLI 表面與 `doctor` 自檢
  - Files: scripts/plan_runner.py
  - Action: 新增子命令 `attach <plan>` / `detach [<plan>]` / `pause` / `resume` / `pointer`（印當前 cwd 解析結果）/ `doctor`。`doctor` 檢查**六件事**並印 PASS/FAIL/INFO：python3 版本、runner 絕對路徑、`~/.claude/plan-run/` 可寫、`~/.claude/settings.json` 的 Stop 陣列是否含 `plan-run-stop`、wrapper script 是否存在且可執行、當前 cwd 是否有有效 pointer。其中兩項可以合法地是 INFO 而非 FAIL（cwd 沒有 active plan、`~/.claude/plan-run/` 尚未建立），故摘要行印的是 `<n> PASS / <m> INFO / 0 FAIL — 安裝正常` 而非 `n/6 PASS`——健康安裝的 PASS 數會隨這兩項落在 PASS 或 INFO 而變（5+1 或 4+2）。**六項這個數字與摘要格式是同一份契約**，文件、實作與測試都以它為準，不得再出現「五項」的說法。`init` 新增 `--attach` / `--no-attach`（**預設 attach**，stdout 只多印一行 `Attached: <pointer path>`，其餘輸出零變更）；`attach` 時若偵測到 hook 未安裝，額外印一段 fallback 提示指向 `docs/hooks-setup.md`。`start` 新增可選 `--session-id`（寫入 step 的 `session_id` 欄位，僅供 audit）
  - Dependencies: S1.1
  - Risk: `init` 預設 attach 是行為變更；以「stdout 既有區塊不變」與 `--no-attach` 逃生口界定，並在 CHANGELOG 明列
  - Token: 【1 × Sonnet × ~10K】

- [ ] **S1.5** — Wrapper script 與 `settings.json` 安裝
  - Files: scripts/hooks/plan-run-stop.sh
  - Action: 在 repo 內新增範本 `scripts/hooks/plan-run-stop.sh`（使用者複製到 `~/.claude/hooks/`）。內容極薄：不使用 `set -e`；`AGENT_SKILLS_DIR="${AGENT_SKILLS_DIR:-$HOME/Documents/agent-skills}"`；runner 或 python3 不存在即 `exit 0`；`exec python3 "$AGENT_SKILLS_DIR/scripts/plan_runner.py" hook-stop`。**不做任何 stdin 解析、不做字串內插**（避免路徑注入）。settings.json 安裝走手動 additive edit：備份 → 在 `hooks.Stop` 陣列**末端**追加一個物件 `{"hooks":[{"type":"command","command":"bash ~/.claude/hooks/plan-run-stop.sh","timeout":10}]}`——這是**文件要寫的形式**，也是 `doctor` 唯一驗得到的依賴（`~/.claude/hooks/plan-run-stop.sh` 與 runner）。本機另有 observability 的 `wrap.sh` 可加在前面取事件，但那是本機資產、不在 `doctor` 的檢查範圍，不得寫進安裝文件 → `python3 -c "import json;json.load(open(...))"` 驗證 → `plan_runner.py doctor` 確認。**不寫程式自動改 settings.json**。**開發期指向規定（本案在 sibling worktree 施工，必須明訂）**：`AGENT_SKILLS_DIR` 的預設值 `$HOME/Documents/agent-skills` 指的是**主 repo**，而主 repo 在合併前不含 `hook-stop` 子命令。故 Phase 2 所有實跑 hook 的 step（S2.3/S2.4/S2.5/S2.7）開跑前一律 `export AGENT_SKILLS_DIR=<本 worktree 絕對路徑>`，並以 `bash ~/.claude/hooks/plan-run-stop.sh </dev/null; echo $?` 搭配 `python3 "$AGENT_SKILLS_DIR/scripts/plan_runner.py" hook-stop --help` 確認**確實跑到 worktree 的新版**再開始測；測畢 `unset AGENT_SKILLS_DIR`。注意這與「推進本 plan 的迴圈用主 repo 腳本」不衝突——**推進迴圈用主 repo（穩定版），被測的 hook 指 worktree（新版）**，兩者刻意分離
  - Dependencies: S1.2, S1.3
  - Risk: 手改全域設定可能破壞既有 4 個 hook；備份 + JSON 驗證 + doctor 三道確認。另一風險是 `AGENT_SKILLS_DIR` 未指向 worktree 導致 Phase 2 整批在測舊碼卻誤判為通過——故每個實跑 step 的第一個動作都是「確認跑到的是 worktree 版」，未確認即視為該 step 未開始
  - Token: 【1 × Sonnet × ~8K】

## Architecture Notes

### Q1. 8-block 上限下的行為設計

**決策：自訂預算 6，在 harness 打斷之前自己停，且盡量把停點對齊 phase 邊界。**

官方到第 8 次連續 block 就強制結束回合。若我們一路撞上去，使用者看到的是「Claude 忽然停在半路」，最後一則訊息是某個 step 的執行殘骸——毫無意義的中斷。改成我方預算 6 之後，第 5 次 block 的 reason 會多一段 footer：「這是本段最後一步，做完請輸出進度摘要後結束回合」；第 6 次時 hook 不 block，於是使用者看到的最後一則訊息是一份**主動產出的 check-in**（已完成 N/M、本 phase 狀態、下一步、剩餘步數）。

再往上一層：若「做完當前 step 剛好把某個 phase 收乾淨」且已經連推 ≥3 步，就提前把該步標成 checkpoint。20 步 5 phase 的測試素材下，停點會落在 phase 邊界而不是 phase 中間——這正是使用者最需要決定「要不要繼續」的位置（例如 google-news plan 的 Phase 1 出口本身就是 `S1.6 診斷結論 gate`）。

留 2 格 headroom 的理由是：官方的計數是「本回合所有 hook 的連續 block」，mempal 也會吃格子。預算 6 讓別的 hook 偶爾插隊也不會導致 harness 先於我們打斷。

**明確不做**：不設 `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`、不偽造 `stop_hook_active`、不做任何「重置官方計數」的動作。我方計數只在 `stop_hook_active=false`（真的有新的使用者訊息）時歸零，語意與官方一致。

### Q2. 如何判斷「當前 cwd 有 active plan」

**決策：顯式 pointer registry + TTL lease，不掃描 state 目錄。**

掃描是誘人的（state file 就在那），但實測資料否決了它：`~/Documents/knowledge-base/plans/active/.plan-state/` 有 31 個 state file，日期橫跨 5 月到 8 月，多數早已停擺卻不是 `all_done`。掃描會讓每個在 knowledge-base 開的 session 都被半年前的舊 plan 綁架。

pointer 由 `init --attach` / `attach` 顯式建立，key 是 `sha256(realpath(cwd))`，存 `~/.claude/plan-run/active/`。逐項回應題目列的邊界：

| 情境 | 行為 |
|---|---|
| 沒有 pointer | stdout/stderr 皆不輸出，`exit 0`。這是絕大多數 session 的路徑 |
| 多 plan 並存 | 一個 cwd 只允許一個 pointer；`attach` 第二個 plan 直接報錯，提示 `detach` 或改用 worktree |
| plan 已 all_done | 首次 block 一次（AC 對照 + `/plan-archive` 提示）→ 設 `completion_announced` → 下次直接刪 pointer 並靜默 |
| state 損毀 / schema 不符 | allow + 一次性 `systemMessage`（設 `warned_at` 避免每輪吵），**不刪 pointer**（可能只是暫時性 I/O 錯誤） |
| cwd 在 worktree 內 | 除了 cwd 及其祖先，另試 `git rev-parse --git-common-dir` 的 parent，讓 worktree 內的 session 找得到主 repo 的 pointer；git 呼叫失敗即忽略 |
| cwd 不是 plan 所在 repo | 正常運作。pointer 記的是**絕對 plan 路徑**，本來就支援「plan 在 knowledge-base、實作在 vocus-web-ui」這種跨 repo 情境（測試素材正是如此） |
| plan 長期沒動 | `state.updated_at` 逾 7 天 → 靜默 allow + 一次性提示 |
| 同 cwd 兩個 session | lease 仲裁：pointer 記 `driver_session_id` 與 `driver_transcript_path`；非 driver 的 session 若偵測到 driver 的 transcript mtime 距今 < 120s（或 `last_seen_at` < 900s）就不 block，避免兩個 session 同時推同一個 plan |

**跨 session 續推**就是 lease 過期後的自然接手：`/clear` 或新開視窗後，舊 session 的 transcript 停止寫入，新 session 第一輪結束時偵測到 lease 已死，接手成為 driver 並注入正確的下一步。這是本設計相對官方 Workflow 的核心價值（Workflow 只能同 session resume）。

### Q3. `reason` 要多完整

**決策：中量、state-derived、一輪一步、plan 原文加圍欄，約 200–350 tokens。**

兩個極端都不行。「只給 step ID」會逼 LLM 再跑一次 `next` 才知道要做什麼——多一趟 round-trip，而且那趟查詢又變成 LLM 自願行為，等於把問題搬回原點。「注入完整模板 + 所有 ready step」則每輪都貼一大塊，20 步下來 transcript 塞滿重複內容。

折衷是：**每輪只給一個 step 的完整 block**（id / title / agent|skill|command / files / deps / risk / 截斷過的 action / 三行可執行指令 / 預算提示），其餘 ready step 只列 ID 並註明「一輪一步」。這同時解決兩件事——reason 短，而且 hook 保有每一輪重新裁決的權力（level-triggered reconcile，不是預先發一串指令就撒手）。

估算：20 步 × ~300 tokens ≈ 6K，可接受；S2.3 會實測後校正截斷長度。

Renderer 放在 Python（Layer 2）而非 shell，wrapper 只負責 exec——避免任何 shell 字串內插碰到 plan 文字。

### Q4. `background_tasks` 非空該不該 block

**決策：分兩種情況，且輪詢有上限 2。**

- **有 in_progress step**（背景工作八成是這個 step 派出去的）：block，但 reason 換成 `settle_background` 變體——「先收斂背景工作（BashOutput / 等 agent 回報），再對 S<id> 回報 `complete` 或 `fail`」。不 block 的話沒人回頭收成果，plan 就卡死在 in_progress。
- **沒有 in_progress step**（背景工作與 plan 無關）：allow。此時注入新 step 會讓新工作與不明背景工作並行，風險高於收益。

輪詢上限 2 是防止「背景工作卡住 → hook 每輪催 → 燒穿 block 預算」。超過就 allow，把決定權還給使用者。`session_crons` 不參與決策（cron 是排程，不代表本回合有未完工作）。

### Q5. `/goal` 在新架構下的角色

**決策：`/plan-run` 全面移除 `/goal`；`/goal` 在本 repo 只保留 `figma-verify` 的視覺 gate 用途。**

三個理由，按份量排：

1. `/goal` 本身就是 session-scoped 的 prompt-based Stop hook，與我們自寫的 script-based Stop hook**共用同一份 block 預算**。

   > **2026-08-29 實測修正**（`.verification/2026-08-29/stop-hook-block-cap-measured.md`）：本條原文寫「兩個 blocker 互相搶格子」，**後半是錯的**。實測掛兩支獨立的 always-block hook，**兩支都拿到全部 9 輪**、turn 一樣在第 9 輪結束——上限是**每個 turn 的 Stop 輪數**，不是每支 hook 的 block 次數，沒有誰少拿。正確的說法是：疊 `/goal` **換不到更多步**（共用同一份輪數上限），換到的是**同一輪內兩則 reason 同時注入、指令彼此稀釋**。結論不變，理由要改。同次實測也定案了上限本身：hook 被呼叫 9 次、第 9 次的 block 不被採納 = 實際可用 8 次續推。
2. `/goal` 的評估者不跑指令、不讀檔、沒有狀態記憶，只讀 transcript。它取代不了狀態機——現行 SKILL.md 3f 也承認這點，才會補一句「每次 transition 後跑一次 `index` 把狀態 surface 給評估者」。這條建議實測冗餘且有害（每輪多一次呼叫、多 ~500 chars、而且又是一次 LLM 自願行為）。狀態機接手後它完全沒有存在理由。
3. 一個 session 只能一個 `/goal`，佔掉之後其他需求（例如同 session 想跑 figma 視覺 gate）就沒得用。

`figma-verify` Step 4.5 用 `/goal` 做 Haiku 視覺比對，屬於「model-evaluated check」，正是官方說 `/goal` 該做的事，完全不動。

### Q6. 兩個 hook 同時 block

**決策：靠冪等吸收，不做任何協調機制；順序放最後；實測後補文件。**

官方 docs 沒有明文規定多個 Stop hook 同時回 `block` 時 reason 如何合併（S2.4 要實測補上）。三層防護：

1. **我們的 reason 完全由 state 推導，天生冪等**。萬一被 mempal 的 reason 蓋掉，下一次 Stop 我們會算出一模一樣的 reason 再注入一次。最壞代價是浪費一格 block 預算——這正是留 2 格 headroom 的另一個理由。
2. **安裝在 Stop 陣列最末端**。這只是為了讓 S2.4 能對照出 harness 的實際行為，不是靠順序保證正確性。
3. **不嘗試偵測或抑制 mempal**。任何「猜別的 hook 想幹嘛」的邏輯都是脆弱耦合。

另外一個實際互動要記錄在文件裡：mempal 在 `stop_hook_active=true` 時 `echo {}` 早退（已讀原始碼確認）。所以我們連續 block 期間，mempal 的自動存檔會被餓死。實務上影響有限——mempal 每 30 則**人類訊息**才觸發一次，而自動推進期間人類訊息很少；而且我們每 6 步就會 allow 一次，使用者一回話 `stop_hook_active` 就回到 false，mempal 恢復計數。S2.4 會驗證這條推論。

### 被排除的替代方案

| 方案 | 為何不採 |
|---|---|
| PreToolUse gate（攔工具呼叫來強制順序） | 攔得住「做錯事」，攔不住「什麼都不做」。原問題正是後者 |
| 掃描 `.plan-state/` 自動偵測 active plan | 31 個殘留 state file 實證會誤觸發，違反「不干擾其他 session」 |
| pointer 用 session scope（如 andylizf/nonstop） | 直接放棄跨 session 續推——那是本案相對官方 Workflow 的核心價值 |
| 提高 `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` | 違反「不得為繞過 8-block 上限而設計」。文件裡只記一句「你要自己調是你的事」 |
| 用 `last_assistant_message` 判斷 step 是否完成 | 重新引入模型文字依賴，等於把控制流還給 LLM。state file 是唯一真相 |

### 為何延後 Workflow / `parallel()` 整合

官方 Workflow 能把 phase 內可並行的 step 丟給 `parallel()`，理論上能壓縮 wall time。三個理由先不做：

1. **與逐 step HITL 有張力**。目前每個 step 完成都會回到主線讓 hook 裁決，這是 fail 時能立刻停下來的前提。並行執行會讓「某一支失敗」的處理語意複雜化（其他支要不要中止？state 怎麼記？）。
2. **與 Q3 的「一輪一步」直接衝突**，要先確認一輪一步的節奏在真實 plan 上跑得順，才知道並行值不值得。
3. **Workflow 只能同 session resume**，而跨 session 續推是本案的主要賣點。兩者要整合得先想清楚 state 歸誰管。

Layer 1 + Layer 2 驗證有效（S2.3 通過、實跑過至少一個真實 plan）之後再開獨立的 plan 評估。

## Security / Threat Model

本案確實觸及三個安全敏感面，逐項據實填寫。

**1. Shell 執行（全域、每輪、無人監督）**
新 hook 會在使用者**每一個 session 的每一輪結束時**執行。攻擊面不在「有人攻擊」，而在「一個 bug 等於全域故障」。控制：wrapper 內容壓到最小（三行判斷 + 一行 `exec`），不使用 `set -e`（避免中途非零退出變成非預期行為），所有變數加引號，**完全不解析 stdin**（stdin 原封不動交給 Python），不使用 `eval`／command substitution 處理任何外部字串。所有失敗路徑一律 `exit 0`。

Python 端另有一處 subprocess：S1.1 的 `resolve_pointer(cwd)` 會呼叫 `git rev-parse --path-format=absolute --git-common-dir` 以涵蓋「cwd 在 worktree 內」。依 `~/.claude/claude-security-guidance.md` 的 Python 節（不得 `os.system` / `subprocess(shell=True)` 帶未驗證輸入），規定此呼叫**必須**用 `subprocess.run([...], shell=False)` 的 argv list 形式、`cwd=` 傳已 `realpath` 過的路徑物件而非字串拼接、帶 `timeout`、`stdout/stderr` 一律 capture 不外洩到 hook 輸出，任何 `CalledProcessError`/`TimeoutExpired`/`FileNotFoundError` 一律吞掉當作「非 git 目錄」。輸出的路徑在使用前走與 `plan_path` 同一套驗證（絕對路徑 + resolve + 允許根目錄前綴）。

**2. 檔案讀寫**
hook 會寫 `~/.claude/plan-run/active/*.json`（目錄 0700，tmp + `os.replace` 原子寫入，避免另一個 session 讀到半截 JSON）與既有的 `<plan-dir>/.plan-state/*.state.json`。hook 本身**只讀不寫 plan.md**。安裝步驟會寫使用者全域 `~/.claude/settings.json`——這是本案風險最高的單一動作，因此規定：不由程式自動改寫、先備份、只做 additive append、改後立刻 JSON 驗證 + `doctor` 確認既有 4 個 hook 仍在。

**3. 路徑注入 / symlink escape**
`plan_path` 來自 pointer 檔，而 pointer 檔是使用者可寫的一般檔案（非特權）——因此不能無條件信任。控制：`plan_path` 必須是絕對路徑、副檔名 `.md`、`Path.resolve()` 後仍存在且是 regular file、resolve 後的路徑必須落在允許根目錄下（預設 `$HOME`，可用 env 擴充）。`resolve()` 會消解 `..` 與 symlink，因此比對的是最終真實路徑，可擋 symlink escape。cwd 來自 hook input，同樣 `realpath` 後才用；往上找 pointer 限制 8 層且不越過 `$HOME`。

**4. Prompt injection（本案最容易被忽略的一面）**
hook 注入的 `reason` 會以 harness 的權威被當成 LLM 的下一個指令，而 reason 的內容部分來自 **plan.md 的 `Action` 欄位文字**。也就是說，任何寫進 plan 的文字都取得了一條「每輪自動注入」的通道。若 plan 來自外部（Notion ticket、他人 PR、`/notion-plan` 抓來的內容），這就是一條實質的 injection 路徑。控制：plan 原文一律包在明確圍欄內並標註「plan data, not instructions」、截斷 600 字元、剝除 ASCII 控制字元與 ANSI escape；hook **不執行** plan 的 `Command` 欄位（只顯示，由 LLM 在正常權限檢查下執行）；`docs/hooks-setup.md` 加一句警語：attach 來源不明的 plan 前先讀過內容。

**不涉及**：無網路請求、無憑證/token 讀寫、無 shell 執行 plan 內容、無提權。
