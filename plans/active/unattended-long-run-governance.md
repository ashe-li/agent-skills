## 1. 需求拆解

使用者原話：「先幫我針對 ~/Documents/agent-skills 設計可以長時間不用介入的方案，可以參考 ~/Documents/agentflow 具體程式或是 skill」。

| # | 子目標 | 現況缺口 | 本 plan 是否處理 |

| N1 | 一輪能推得更遠 | harness 硬限制一輪 8 步，`/goal` 與 Stop hook 共用同一上限，多掛驅動器換不到更多步 | **不處理**（物理上限，見 §3 架構決策） |

### 2.1 Plan 指紋（漂移偵測）

`init_state()`（`scripts/plan_runner.py:571`）把 plan.md 的 SHA-256 寫進 state 的 `plan_sha256` 欄位；`load_state()`（:470）每次讀取時重算並比對。不符時：

- `status` / `next` 輸出頂部印 `DRIFT:` 警告，附「plan.md 已變更但 state 是舊快照」與修法（`rm <state> && plan_runner.py init`）
- `next` **預設拒絕派下一步**，逃生口 `--ignore-drift`
- 既有 state 缺 `plan_sha256` 欄位 → legacy 放行，只印一次性 hint，不 block

依據既有教訓 `wiki/learned/plan-state-json-is-a-snapshot-not-a-pointer-plan-edits-are-silently-ignored.md`：修法是「改完 plan 要 rm state 再 init」，`init` 對既有 state 無 `--force` 會拒絕（:2808-2813），`--force` 則呼叫 `init_state()`（:2814）整份重建，全 PENDING 的賦值在該函式內（~:585），不 merge。這個機制不改變修法，只是把「靜默」變成「顯式」。

### 2.2 停機標記 `.plan-state/<slug>.stop.md`

借鏡 `agentflow/skills/agentflow/scripts/looper.js:20` 的 `.stop.txt` —— **不可續跑標記，需人工審過才清掉**。內容是 Markdown（不是 JSON），因為讀者是人：

```
# STOP — <slug>
- Stopped at: <ISO8601>
- Failing step: S2.3 — <title>
- Git HEAD: <sha> (<branch>, dirty: yes/no)
- Reason: <一段話，禁止貼 log 原文，禁止貼任何 token/secret>
- Suggested next: <一行可執行的建議>
```

`next` 與 Stop hook 在做任何事之前先檢查此檔存在 → 立即 `allow`（自然收手，不再 block 推進）並在輸出印出全文。清除需人工 `rm`，或 `plan_runner.py stop --clear --reason-reviewed`（旗標避免手滑）。

**關鍵安全性質**：stop.md 是 user-writable，其內容**只作提示，不作控制流授權**。程式只判斷「檔案是否存在」，不解析內容決定行為。

### 2.3 落檔 checkpoint + wall-clock 觸發

兩件事合起來才有意義：

**(a) checkpoint 內容契約** —— `.plan-state/<slug>.checkpoint.md`，借鏡 AgentFlow 的 10 分鐘 WIP checkpoint（`agentflow/skills/agentflow/SKILL.md:62`）四要件：`Finished` / `Running now` / `Still to do` / `Next work action`，加上自足性規則：**checkpoint 不得要求讀者回頭讀 plan.md、state.json 或前一則 checkpoint 才看得懂**。既有 `checkpoint_pending` 旗標從「只是一個 bool」升級為「觸發寫檔的訊號」：hook reason 明確要求 agent 在停下前把這四段寫進檔案。

這**不打斷使用者** —— 寫進檔案，不是寫進聊天視窗，與 `rules/common/reporting-cadence.md` 的「跑完整條鏈再一次回報」無衝突。

**(b) wall-clock 觸發** —— `decide_budget()`（def 在 :1562）目前只看 `consecutive_blocks` 這個 turn 計數。新增第四條規則：距 `pointer['last_advance_at']` 超過 `CHECKPOINT_STALE_SECONDS`（預設 45 分鐘，env `PLAN_RUN_CHECKPOINT_STALE_SECONDS` 可調）→ 也設 `checkpoint_pending`。

**設計約束**：`decide_budget()` 目前是純函式（docstring 明寫 "Pure: only reads pointer/state, never writes the pointer file back"）。必須用注入而非讀時鐘保持可測：簽章改為 `decide_budget(pointer, state, ready_step, *, now: float | None = None)`，caller 傳 `time.time()`，測試傳固定值。**不可在函式內直接呼叫 `time.time()`**，否則毀掉既有 golden test 的可決定性。

### 2.4 工作量路由

借鏡 `agentflow/skills/agentflow/scripts/round-linter.js` 的 `large_work_route`（`estimated_hours*60 > large_work_minutes` → fail，:2681-2685）。輕量版：

### 2.5 auto-reply：例行問題自答，非例行照舊問

這是本 plan 唯一直接減少「中斷次數」的機制，其餘四個都只改善「中斷品質」。

#### 借鏡來源

AgentFlow 的 `auto-reply: on|off` 設定，語義是「AI 可不可以自己回答自己提出的例行問題、不等你就繼續工作」，新專案預設 `on`（`agentflow/skills/agentflow/docs/AG_GUIDE.zh-tw.md:119`、`docs/AG_GUIDE.md:137`）。

`SKILL.md:104` 的規範句：「`auto-reply: on` resolves only safe routine defaults. `keep-going` enables it temporarily for the current open list, then resets it. Owner-only choices, irreversible work, and new outward channels always stop for the owner.」

#### 四類硬停止（安全信封，逐字照抄）

`AG_GUIDE.zh-tw.md:119`：「但有四件事不管怎麼設都一定停下來等你：**只有主人能做的決定、無法復原的事、會透過新管道離開你機器的事、超過約定花費上限的事。**」

這四句是整個機制的安全信封。落到 agent-skills，每一類都對映到使用者既有的規則，因此**判定條件不是新發明的，是把既有規則寫成程式可判定的形式**：

| # | 硬停止類別 | agent-skills 的程式可判定條件 | 對映的既有規則 |
|---|---|---|---|
| H1 | 只有主人能做的決定 | step 的 `Action` 命中設計參數／視覺裁決／履歷或對外文案／≥3 項並列選擇；或 plan 中標 `Owner:` 的 step | `feedback_designer_spec_no_unilateral_change`、`feedback_explicit_list_before_authorize`、`feedback_group_decisions_not_per_item`、模型分工（主模型才做視覺裁決） |
| H2 | 無法復原的事 | 命令位置出現 `rm`／`git push --force`／`git reset --hard`／`git stash`／`drop`／`delete`／`kubectl delete`；或萬用字元批次刪除 | `feedback_pre_destroy_three_axis_check`、`feedback_force_push_confirm`、`feedback_delete_explicit_paths_no_wildcard`、`rules/common/git-workflow.md` |
| H3 | 會透過新管道離開機器的事 | 對外送出（`gh pr create/merge/comment`、Notion 寫入、Slack、寄信）；或觸及後端 own 資源（`smb-*`／`payment-*` helm values、prod cloudflared/alloy、cert-manager）；或 dev 指向 prod API | `rules/common/repo-ownership.md`、`feedback_no_dev_pointed_to_prod_api`、`feedback_auto_merge_small_infra_prs`（只有微調 PR 可 auto-merge） |
| H4 | 超過約定花費上限的事 | 單一 step 實際消耗超過 plan §10 該 step 預估 token 的 **2 倍**；或 phase 累計超過小計 1.5 倍 | plan 的 Token 預算章節、`dispatch-loop/SKILL.md` 的 token 紀律 |

**H2/H3 的命令判定必須錨定在命令位置，不是字面出現** —— 直接引用 `wiki/learned/guard-regex-must-anchor-on-command-position-not-word-presence.md` 的教訓，這條 guard 已經寫錯過一次。

#### 落點：state JSON 的 `auto_reply` 欄位

**建議寫進 state JSON（`auto_reply: "on"|"off"`，預設 `"off"`），不另開 `settings.json`。** 三個理由：

1. **單一真相來源**：state 已是 per-plan 的唯一真相來源，新欄位直接沿用；另開一個檔就多一個「settings 與 state 不同步」的漂移面，而漂移正是本 plan 花 §2.1 一整節在防的東西。

   > **前提修正（2026-09-07，S4.2 執行時發現）**：本條原文宣稱「`load_state()` 已有完整 validation 與 legacy 放行路徑」，**該前提為假**。實查 `load_state()` 只有 4 行（`exists()` 檢查 + `json.loads`），**無 validation、不捕捉 `JSONDecodeError`**——壞掉的 state 會讓 `next` 直接 traceback。有 validation 的是 **pointer** 不是 state。結論（放 state 而非另開設定檔）不受影響，它靠的是「避免第二個漂移面」這個獨立論據；但這個缺口是真的，**已列入 S5.1 必須處理的項目**。
2. **失效方向是安全的**：`init --force`（:2814 呼叫 `init_state()`）會整份重建 state，也就是說 `rm state && init` 這個 drift 修法會**清掉 auto_reply 設定、退回預設 `off`**。退回 off = 每題都問人 = fail-safe。若放在獨立 settings.json 反而會在 plan 已經改過的情況下**存活下來**，那才危險。
3. **版控與權限一致**：`.plan-state/` 的版控策略在 S1.2 只需裁定一次。

**與 AgentFlow 的一個刻意差異：預設 `off`，不是 `on`。** AgentFlow 新專案預設 on，我們預設 off，理由是向後相容——其他共用 `plan_runner.py` 的 repo 既有的 state沒有此欄位，缺欄位必須等同 `off`，否則升級後其他 repo 所有進行中的 plan 行為靜默改變，那正是 §2.1 在防的失敗模式。開啟是使用者的明示動作。

#### 課責：`Auto-answered:` 區塊（不可省）

AgentFlow 的關鍵設計不是「可以自動答」，而是「自動答**必須在同一份報告裡寫明為什麼那個答案是安全的**」（same-pass provenance，`references/advisors/requirements.md:13`；`references/ag.md:72` 進一步規定 owner-only／衝突／失敗／缺證據／hard-stop 一律保持 open）。

落到 agent-skills：`.plan-state/<slug>.checkpoint.md`（§2.3 已設計的檔案）新增第五個區塊：

```
## Auto-answered
- Q1: <被自動決定的問題原文>
  - Took: <採用的預設值>
  - Safe because: <為什麼這是安全的例行預設，一句話>
  - Hard-stop check: H1 no / H2 no / H3 no / H4 no
```

**規則：沒有這段就不准自動答。** 也就是說 auto-reply 的啟用條件包含「checkpoint 落檔機制已就緒」——這是 S4.3 依賴 S3.1 的原因。`Hard-stop check` 四項全 `no` 才成立，任何一項 `yes` 就必須保持 open 並停下。

#### `keep-going` 等價物

一次性旗標 `plan_runner.py next --keep-going`：只對**當前這批未決項**開啟 auto-reply，該次 `next` 結束後自動重設回 state 中的原值，**不寫回 state**。用途是「我現在坐在這裡，這批小問題你自己決定，我等下就走」。四類硬停止在 `--keep-going` 下**同樣生效**，不因臨時旗標而放寬。

#### 與既有「要問使用者」規則的關係（重要）

這個機制**不廢除**任何既有的提問規則，它做的是**把「什麼算例行」界定清楚，非例行的照舊問**：

| 既有規則 | auto-reply 開啟後 | 為什麼 |
|---|---|---|
| `feedback_task_tracking_askuser_default_enabled`（複雜任務問是否啟用 task tracking） | **照舊問** | 這是 session 層級的模式選擇，不是 plan 內的例行預設；且使用者明示「用 AskUserQuestion 問，不自動啟用」 |
| `feedback_group_decisions_not_per_item`（>10 項待裁決先分群再問） | **照舊問，但分群後群內的例行項可自動答** | 分群本身是 owner-only（H1）；群內若全是安全預設值則可批次自動答並逐筆留痕 |
| `feedback_explicit_list_before_authorize`（≥3 決策先列 list） | **照舊問** | 明確落在 H1 |
| Teammate 編隊 / 模型分工的 AskUserQuestion | **照舊問** | 涉及 token 預算承諾，落在 H4 的精神 |
| step 內部的實作細節選擇（檔名、測試命名、錯誤訊息措辭、既有慣例的沿用） | **可自動答** | 這才是「安全的例行預設」——有既有慣例可循、可逆、不對外、不超預算 |

一句話界定：**「例行」＝有既有慣例可循、完全可逆、不離開本機、不超預算，四者同時成立。** 缺任何一項就不是例行。

### 2.6 開跑前四選一確認閘門（已移除）

> **移除告示（2026-09-08，使用者裁決）**
>
> 本節保留為設計紀錄，**機制不存在於程式中**。S4.4 的全部產出已移除，`next` 對超門檻 phase 的行為回到 §2.4 的 warn-only 警告。
>
> **移除理由（兩層）：**
>
> 1. **技術層**——三條干擾項規則是「拿正確答案往三個互不相交的方向各擾動一次」，因此**正確答案恆等於四個選項的逐元素多數決**：任一屬於正確答案的元素必然出現在多數選項，任一不屬於的只可能來自單一條規則、必然只出現一次。兩份 fixture 實測，多數決還原的 Files 與 Steps 皆與正確答案完全相符且唯一命中。三次 fresh-context 盲測全部答對，零專案知識。要破壞這個性質就得讓干擾項共用擾動，但那會讓它們不再對應「三種真實誤解」，正是 §6 禁止的「靠加難度硬撐」。
> 2. **目的層（決定性的一層）**——本 plan 的目標是**減少中斷**。這個閘門加一次停，唯一的正當性是換到「確認過的理解」；那個產物被證明不存在後，剩下的是純成本，方向與整份 plan 相反。§6 原本預留的降級退路（範圍摘要 + 單純確認）**同樣被否決**：它保留了停頓卻仍然買不到理解。**一個買不到東西的閘門，即使技術上有效，仍然只是成本。**
>
> **判準（可復用）：加一次停，必須換到東西。** §2.2 的 `stop.md` 也加停，但它停的是「已知壞掉的推進」，停下來就是正確結果，所以它留著。
>
> `Confirmed scope:` 的範圍凍結價值（§3 決策 5 稱它為路線 B 的前置）**隨本機制一併失效**，路線 B 若日後啟動需另案設計——不要從這裡撿。


#### 問題：yes/no 確認擋不住任何東西

一般的「確定要跑嗎？（y/n）」在無人值守情境下是失效的儀式。人會反射性按 yes——**尤其在準備離開電腦、想趕快讓它跑起來的時候，而那正是最需要看清楚的一刻**。一個只需要按 y 的閘門，測不出人到底知不知道即將發生什麼。

#### 做法：把確認改成一題有正確答案的選擇題

`next` 在進入一個 `Estimated:` 小計超過 `LARGE_PHASE_MINUTES` 的 phase **之前**，用 `AskUserQuestion` 出一題四選一：其中一個選項是即將執行內容的正確摘要，另外三個是似是而非的干擾項。**選對才放行。**

**正確答案從 state 直接生成，不是自由發揮**——四個來源：該 phase 全部 step 的 title、`Files:` 欄位聯集、`Estimated:` 小計、會動到的既有行為（從 step 的 `Action` 中標記為 behavior change 的部分）。生成是決定性的，同一份 state 每次產出同一段文字。

#### 干擾項生成規則（機制成不成立的關鍵）

這是整個機制唯一有技術含量的地方。**若干擾項隨機亂編，使用者一眼就挑得出來，閘門形同虛設**——而且比沒有閘門更糟，因為它給人「已經確認過」的錯覺。三個干擾項必須來自**真實會發生的誤解**：

| 干擾項 | 生成規則（從 state 決定性推導） | 對應的真實誤解 |
|---|---|---|
| **範圍過寬** | 併入**下一個 phase** 的 `Files:` 聯集 | 「我以為它會一路做到底」 |
| **範圍過窄** | 拿掉該 phase 中**依賴深度最大**的 step 及其 `Files:` | 「我以為只是改個小地方」 |
| **動到禁區** | 把 `Files:` 中的測試檔換成 golden baseline（`scripts/tests/golden/`），或把目標 repo 換成鄰近 repo（`agent-skills` ↔ `knowledge-base`） | 「我沒發現它會動到那個」 |

**第三種有直接的實證依據**：本 plan 撰寫過程中就真的犯過這個錯——把 `knowledge-base` 的 state 份數當成 `agent-skills` 的（見 §1 的前提修正與 S1.2 的 `Why:`）。鄰近 repo 混淆不是假想的誤解類型，是這份 plan 自己踩過的。

#### 選錯的處置：不是拒絕，是釐清

選錯**不代表不准跑**。選錯代表使用者對即將發生的事有誤解——**那正是閘門要抓的東西**，抓到了應該處理它而不是懲罰它。處置分兩級：

1. **第一次選錯** → 印出正確答案、逐項標出與所選項的差異（多了哪些檔、少了哪個 step、動到哪個禁區）、**重新問一次**
2. **第二次仍選錯** → 寫 `stop.md` 停機（§2.2 的機制）。理由：此時問題已經不在確認流程，而在 **plan 本身講不清楚**——一份講不清楚的 plan 不該在無人值守下跑

#### 選對的產物：`Confirmed scope:` 權威範圍宣告

選中的那段文字**寫進 `checkpoint.md` 的新區塊 `Confirmed scope:`**，附時戳與 phase 名：

```
## Confirmed scope
- Phase: Phase 4 — 少停與確認
- Confirmed at: <ISO8601>
- Scope: <選中的那段文字，逐字>
```

這不只是紀錄，是**該批工作的權威範圍宣告**：後續 agent 若想擴大範圍，以此駁回。等於把 AgentFlow 的 I-054（`references/delegation.md`：worker findings 不能自動變成 work，除非能指名 owner 的原句或既有義務）落地成一段**可以逐字比對的具體字串**——agent-skills 現在沒有這個錨點，「範圍蔓延」只能靠人事後察覺。

#### 與機制 5（auto-reply）的交界（必須明寫）

**這一題屬於四類硬停止的第一類「只有主人能做的決定」（H1）。auto-reply 永遠不得自動作答，`--keep-going` 也不行。**

這是兩個機制唯一會打架的地方，因此必須有**專屬守衛測試**：`auto_reply="on"` 加 `--keep-going` 的組合下，四選一閘門仍然停下來等人。若這條守不住，機制 5 就會把機制 6 整個吃掉——一個能被自動作答的確認題，比沒有確認題更糟。

#### 觸發頻率與對機制 4 的升級

**只在進入超門檻 phase 時問一次，不是每步問。** 未超門檻的 phase 完全不問。

機制 4（§2.4 工作量路由）因此從「只警告」**升級為「警告 + 確認閘門」**，兩者共用同一個 `LARGE_PHASE_MINUTES` 判定，不引入第二套門檻。§2.4 原本寫「只警告，不 block」的理由是「我們沒有外層 looper 承接失敗，硬 block 只會卡住使用者」——四選一閘門正是那個缺失的承接機制：它不是無條件 block，是**給一條可以走過去的路**。

## 3. 架構決策

### 決策 1（核心）：採路線 A（harness 內），排除路線 B（harness 外驅動器）

#### 選 A 的三條理由，按重量排序

**(1) B 的前置條件正好是 A 的產出，順序不能倒。**

AgentFlow 的 looper 之所以敢無人值守跑，不是因為它有 `spawn()`（`looper-git.js:71`：`spawn(worker.command, args, {cwd, shell:false})`），而是因為它周邊有一整套治理：

- `.stop.txt` 不可續跑標記（`looper.js:20,442,641`），失敗即停，人工審過清掉才能重跑
- `.looper-attempt.json` 逐欄 identity 核對（`:1038-1060`：plan identity sha256/dev/ino/size、exit_code、completion_matches、archived）
- 逐字比對的 `completion_line`（`:721-729`、`:1626`）：摘要、報告、commit、裸完成訊號都不算完成
- queue envelope 凍結（`.queue-generation.json` + fingerprint digest）
- round-linter 三條強制長跑檢查，由 `stop-hook.js:93` 每輪呼叫、`:108` block

**agent-skills 現在這些一條都沒有** —— grep `dispatch-loop/`、`plan-run/`、`ship-ticket/`、`rules/` 找 checkpoint／heartbeat／長跑，零命中。先蓋 B 等於讓一個無人值守迴圈在沒有停機標記、沒有漂移偵測、沒有完成判定的地基上跑，這正是把治理欠債交給最不該承擔它的執行者。

**(2) B 的收益被高估。**

B 突破的是「一輪 8 步」，但 8 步 ≠ 8 分鐘。實際卡住 plan 的從來不是步數上限，而是三類已經踩過的坑：

- 改了 plan.md 卻沿用舊快照（`wiki/learned/plan-state-json-is-a-snapshot-not-a-pointer-plan-edits-are-silently-ignored.md`）
- step regex 誤判任何含 step id 的 checkbox（`wiki/learned/plan-runner-step-regex-matches-any-checkbox-with-step-id.md`）
- `plan status` 欄位不可信，要靠 git log 驗（`wiki/learned/plan-status-fields-unreliable-verify-via-git-log.md`）

這三個 B 一個都不解決，反而在無人值守下放大它們的損害半徑——沒有人在看終端時，靜默走錯會一路推到底。

**(3) B 的安全面在無人值守下無法用「小心一點」收斂。**

逐條見 §7.2。摘要：子程序完整繼承使用者憑證（gh token、kubeconfig、AWS profile），而使用者規則明確禁止碰後端 own 的資源（`rules/common/repo-ownership.md`）、禁 force-push、禁 `git stash -u`。要在 headless 子程序裡落實這些圍欄，等於重寫一層權限系統——那是比本 plan 大一個數量級的工程。

#### 被排除的路線 B：具體評估

**B 長什麼樣**：仿 `looper.js` 的 `run_plans` 迴圈寫一個外層 Python/Node 驅動器，逐 step 或逐 phase 用 `claude -p`（headless）spawn 子程序，外層迴圈負責排程、心跳、完成判定、失敗停機。因為驅動器在 harness 外，不受 8 步上限約束。

**要讓 B 安全上線，必須先補齊的清單**（每一項都是獨立工程量）：

| # | 缺件 | AgentFlow 對應 | agent-skills 現況 | 估計規模 |
|---|---|---|---|---|
| B1 | 不可續跑停機標記 | `.stop.txt` | 無 | 小（= 本 plan S2.2） |
| B2 | plan identity 凍結與核對 | `.looper-attempt.json` 逐欄比對 | 無（= 本 plan S2.1 的加強版） | 中 |
| B3 | 完成判定（防「摘要當完成」） | 逐字 `completion_line` + notebook 結構檢查 | 無 | **大** |
| B4 | 破壞性操作圍欄（命令攔截層） | 無對應（AgentFlow 也沒有） | 無 | **大** |
| B5 | 成本上界 / deadline | `DEFAULT_TIMEOUT_MS=0`，預設全關 | 無 | 中，且 AgentFlow 的經驗顯示不可靠 |
| B6 | watchdog / stall 偵測 | `process.kill(pid,0)`+`ESRCH`（`looper.js:1079-1088`）、`external-runner.js:395-410` | 無 | 中 |
| B7 | context 管理（notebook compaction） | 500 行門檻 + `resume-intake.js:12-15` bounded 讀取 | 無 | 中 |
| B8 | **無人值守決策授權**——headless 子程序沒有人可以回答 `AskUserQuestion` | `auto-reply` + 四類硬停止（`AG_GUIDE.zh-tw.md:119`） | 無 | 中（= 本 plan §2.5，見決策 4） |
| B9 | **起跑前的範圍凍結**——沒人在看時，worker 擴大範圍無物可擋 | I-054 的 owner 原句溯源（`references/delegation.md`），但無起跑前閘門 | 無 | 小（= 本 plan §2.6，見決策 5） |

**B8 特別值得注意**：它看似最小，實際上是 B 的**啟動條件**——沒有它，外層迴圈 spawn 的子程序會在第一個決策點卡死到 timeout，而 B5 已經說明 timeout 不可靠。本 plan 的 §2.5 正好把 B8 做完（見決策 4）。

B3 與 B4 各自都是專案級工程，而且沒有一個能靠「派個 agent 寫一下」完成：

- **B3**：使用者規則明訂「CI 綠 ≠ 完成，要可觀察的驗收證據」（完成兩級門檻）。無人值守下沒有第二雙眼睛做這個判定，而 AgentFlow 用了逐字比對加 notebook 結構雙重檢查才勉強擋住造假。
- **B4**：`wiki/learned/guard-regex-must-anchor-on-command-position-not-word-presence.md` 這條教訓本身就說明了命令攔截器有多容易寫錯——用「字面出現」而非「命令位置」錨定的 guard 會漏。

**B5 的反證特別值得記下**：AgentFlow 的 deadline timer 與 stall detector **兩者都 opt-in 且預設全關**（`DEFAULT_TIMEOUT_MS=0`，`external-runner.js:10`）。由來是 I-050（`docs/incidents-log.md:307`）：曾在 10 分鐘砍掉 worker，重啟後那個 worker 跑了 54 分鐘、707 個測試通過。`delegation.md:37` 明文寫下結論：「Silent reasoning or unchanged files alone never prove a hang」。也就是說，連做過這件事的 AgentFlow 都認定 timeout 不可靠而選擇不設——無人值守的 token 消耗因此沒有上界。

**明確承認 A 放棄了什麼**：A 不會讓 plan 一次跑完 20 步。A 的承諾是「每 8 步停一次，但每次停都停得乾淨」。如果使用者的真實需求是「我睡覺時它跑完整個 plan」，A 不滿足，需要另開 B 的專案。**這一點應該在使用者確認 plan 時被明確回答（見 §13）。**

#### 混合的可能性（不在本 plan 範圍，但設計上預留）

A 的四個落檔產物——`plan_sha256`、`stop.md`、`checkpoint.md`、`Estimated:`——恰好就是 B 需要的 IPC 介面：

| A 的產物 | B 未來會怎麼用 |
|---|---|
| `.plan-state/<slug>.stop.md` | 外層迴圈每輪開始前讀，存在即不續跑（= B1 直接滿足） |
| `plan_sha256` | 驗 plan.md 未被置換再起下一輪（= B2 的一半） |
| `.plan-state/<slug>.checkpoint.md` | 組下一輪 headless prompt 的輸入，取代 AgentFlow 的 notebook（= B7 的替代路徑，且天生 bounded） |
| `Estimated:` | 決定該 step 的 deadline 與是否該拆（= B5 的輸入） |
| `auto_reply` + 四類硬停止 | **B4（破壞性操作圍欄）的判定邏輯與安全信封**——B 只需把同一組條件從「要不要問人」改判成「准不准執行」 |
| `Confirmed scope:` 區塊 | **範圍凍結錨點**——外層迴圈每輪把它塞進子程序 prompt，收工時比對實際動到的檔案是否超出宣告 |

**所以 A 不是 B 的替代品，是 B 的第 0 階段。** 未來若要做 B，剩下的只有 B3（完成判定）、B4（破壞性操作圍欄）、B6（watchdog）三件，不必回頭補地基。

### 決策 2：checkpoint 落檔，不落聊天視窗

**被排除的替代方案**：讓 hook reason 直接要求 agent 在聊天視窗輸出進度摘要。

**排除理由**：直接違反 `rules/common/reporting-cadence.md`（「跑完整條鏈再一次回報，中途只在卡住或需裁決時出聲」），且聊天視窗的內容在 `/compact` 後會消失——恰好是最需要它的時刻。落檔則同時滿足「不打斷」與「跨 session 存活」兩個條件。

### 決策 3：drift 時 `next` 預設 block

**被排除的替代方案**：只印警告不 block。

**排除理由**：「靜默沿用舊快照」已經踩過一次，而印了不 block 在無人值守情境下等於沒印——沒有人在看終端。逃生口 `--ignore-drift` 保留給「我知道我在做什麼」的情況。這是本 plan 唯一的 behavior change，需在 CHANGELOG 標明。

### 決策 4：auto-reply 屬於路線 A，且是路線 B 的必要前置

**為什麼它屬於 A 而不是 B**：auto-reply 完全不需要外層驅動器。它改的是「harness 內的流程要不要停下來發 `AskUserQuestion`」，執行模型一步都沒變——沒有 spawn、沒有新程序、沒有排程器。它純粹是在既有的 8 步天花板之下，把被浪費在「停下來問人」的輪次拿回來。

**為什麼它是 B 的必要前置**：路線 B 的外層迴圈 spawn 的是 headless 子程序（`claude -p`），headless 沒有人可以回答 `AskUserQuestion`。因此**若流程還會停下來問，外層迴圈也推不動**——子程序會卡在提問處直到 timeout，而 §3 已經論證 timeout 不可靠。也就是說 B 若沒有 auto-reply，它突破 8 步上限所換來的續航力會被提問阻斷，等於白做。

**這也是 §3 決策 1「A 是 B 的第 0 階段」的最強證據**：四類硬停止的判定邏輯，在 A 裡是「要不要問人」，在 B 裡就是「准不准執行」——同一組條件，換一個輸出。先在有人監督的 A 環境把這組條件磨對，再交給無人值守的 B 使用，順序不能倒。

**被排除的替代方案**：全域開啟 auto-reply（寫進 `~/.claude/settings.json` 或 CLAUDE.md）。排除理由：安全信封的判定是**per-plan 情境相依**的——同一個 `rm` 在清 scratchpad 與清 `.verification/` 是完全不同的風險等級（後者違反「證據不得刪除」規則）。全域旗標無法承載這種情境差異，只會退化成一個危險的總開關。

### 決策 5：四選一閘門屬於路線 A，且是路線 B 的範圍凍結前置

**為什麼屬於 A**：它是一次 `AskUserQuestion` 加一段從 state 決定性生成的文字，執行模型完全沒變——沒有 spawn、沒有新程序、沒有外層排程。它甚至比其他五個機制更「純 harness 內」：其他機制多少會改變 `next` 的控制流，這個只是在既有的 phase 邊界插入一次提問。

**為什麼是 B 的前置**：路線 B 的外層迴圈一旦起跑就沒有人在看。**若起跑前沒有把範圍凍結成一段可比對的字串，跑歪了沒有任何東西擋得住**——B 的 worker 是 headless 子程序，它擴大範圍時不會有人察覺，而 §3 已論證 B3（完成判定）與 B4（破壞性操作圍欄）都缺席。`Confirmed scope:` 正是 B 需要的那個錨點：外層迴圈可以在每輪把它塞進子程序的 prompt，並在收工時比對實際動到的檔案是否超出宣告。

**與 B8 的分工**：B8（無人值守決策授權，§2.5）解決「沒人可以回答問題」；機制 6 解決「沒人確認過範圍」。兩者都是 B 的啟動條件，但方向相反——前者是讓流程**不必問**，後者是確保**該問的那一次真的問了、而且問得有效**。這也是為什麼機制 6 被明訂為 auto-reply 永不可自動作答的 H1 類別。

**被排除的替代方案**：把確認做成「顯示範圍摘要 + y/n」。排除理由見 §2.6 開頭——y/n 測不出理解，只測得出手指。但這個被排除的方案是機制 6 的**降級退路**（見 §6 的「尚待驗證的假設」）：若四選一的干擾項被證實太弱，退回這裡仍能保住 `Confirmed scope:` 的產出價值。

**破壞性變更兩項**：

1. drift 時 `next` 會 block（決策 3）
2. **超過 `LARGE_PHASE_MINUTES` 的 phase 起跑前多一次四選一確認**（決策 5）——未超門檻的 phase 完全不受影響；`Estimated:` 是選填欄位，沒填的 plan 小計為 0，永遠不觸發

### 效能影響

`load_state()` 每次多讀一次 plan.md 並算 SHA-256。plan.md 量級是數十 KB，`hashlib.sha256` 在此量級 <1ms，相對於既有的 `GIT_SUBPROCESS_TIMEOUT_SECONDS=3` 子程序呼叫可忽略。`stop.md` 檢查是一次 `Path.exists()`。`decide_budget` 新規則是兩次浮點比較。**無新增子程序、無新增網路呼叫、無新增 regex。**

### 安全影響（摘要，詳見 §7）

路線 A 不新增執行面（no spawn、no network、no credential handling），只新增三個寫檔點，全部在既有已寫入的目錄下（`plans/*/.plan-state/`）。主要風險有三類：「寫進 repo 的檔案可能被 commit 且夾帶敏感內容」、「user-writable 檔案被誤當授權來源」，以及 **auto-reply 引入的「錯誤的例行判定會讓不該自動做的事被自動做掉」**——第三類是本 plan 中唯一會改變「什麼事會在沒有人確認下發生」的機制，因此在 §7.1 有獨立的三條處置（T11–T13）。

### 尚待驗證的假設（機制 6）

機制 1–5 都有外部前例可循——AgentFlow 的 `.stop.txt`、WIP checkpoint、round-linter、auto-reply 各有已驗證的實作。**機制 6 沒有：AgentFlow 沒有對應設計，這是本 plan 唯一原創的機制。**

**最大未知**：干擾項生成規則夠不夠強。三條規則（範圍過寬／過窄／動到禁區）是從「真實會發生的誤解類型」推導的，其中第三條有本 plan 自己踩過的實證，但**整體無實測基礎**——沒有人測過一個不讀 plan 的人能不能靠語感挑出正確項。

**驗收方式**：AC22——由沒參與規劃的人或 fresh-context agent 實際作答。**若能不讀 plan 就挑對，即 FAIL。** 這是機制 6 唯一有意義的驗收，其他 AC 只驗生成規則有沒有照做。

**FAIL 時的處置（預先講死，避免屆時硬撐）**：

**降級為「顯示範圍摘要 + 單純確認」，保留 `Confirmed scope:` 的產出價值，再另案重新設計生成規則。**

**不要靠加難度硬撐。** 把干擾項做得更刁鑽，換來的是使用者選錯率上升、第二次選錯就寫 `stop.md`——閘門從「測理解」退化成「測運氣」，而它擋住的是一個本來該跑的 plan。**一個猜得到的四選一比沒有閘門更糟，一個猜不到的四選一比停機更糟。** 兩邊都不對的時候，退回單純確認至少保住了 `Confirmed scope:` 這個範圍凍結錨點——那才是機制 6 對路線 B 的真正貢獻（決策 5、缺件 B9）。

| T14 | 四選一選項文字由程式生成後送進 `AskUserQuestion`，可能把敏感內容帶進選項 | **是** | 選項文字的來源是 state 中的 `Files:` 路徑、step title 與 `Estimated:` 數字——**路徑本身可能洩漏目錄結構，但不含檔案內容**。三條處置：(a) 選項只帶**相對 repo root 的路徑**，不帶絕對路徑（避免洩漏使用者家目錄結構）(b) 不從 `Action:` 自由文字整段複製，只取標記為 behavior change 的部分 (c) `Confirmed scope:` 寫入 checkpoint 時**受既有內容規則約束**（禁 log 原文、禁任何 token/key/JWT，同 T4）。另注意「動到禁區」干擾項會刻意產生**不真實的路徑**，該文字若被誤存進 `Confirmed scope:` 會造成錯誤的範圍宣告——因此只有**選中的正確項**可寫入，干擾項一律不落檔 |

**結論：路線 A 的威脅面收斂為兩組。** 第一組是「本機寫檔的路徑、內容與信任邊界」（T3、T4-T5、T6-T7），處置已覆蓋，無殘餘高風險項。第二組是決策自動化與確認的邊界（T11-T14）：auto-reply 擴大了自動化範圍，四選一閘門則反向收窄了它（機制 6 明訂為 H1，永不可自動作答）。這是本 plan 唯一擴大自動化範圍的地方，因此採**反面白名單 + 預設關閉 + 強制留痕 + 逃生口**四道防線，且判定條件一律溯源既有規則。**殘餘風險**：安全信封漏掉某一類人類會停下來想一下的情境。此殘餘風險由「預設 off、需使用者明示開啟」承接——開啟是一次知情決定，不是預設狀態。

### 7.2 路線 B（被排除）為何在安全上不可接受

列出以說明排除有據，非規避：

1. **憑證繼承無法收斂**：`spawn(cmd, args, {cwd, shell:false})` 的子程序繼承完整 env——`gh` token、`kubeconfig`、AWS profile 全在裡面。無人值守下沒有人能攔截一次錯誤的 `kubectl delete` 或 `gh pr merge`。
2. **破壞性操作圍欄不存在且難寫對**：使用者規則要求「碰後端 own 或歸屬不明的資源 → 不動」、禁 force-push、禁 `git stash -u`、禁 dev server 指向 prod API。要在 headless 子程序裡落實，需要一層命令攔截器，而 `guard-regex-must-anchor-on-command-position-not-word-presence` 這條教訓正說明了這種攔截器有多容易寫成漏的。
3. **完成判定造假**：使用者規則明訂「CI 綠 ≠ 完成，要可觀察的驗收證據」。AgentFlow 用逐字 `completion_line` 加 notebook 結構檢查（`looper.js:721-729`、`:1626`）才勉強擋住「摘要當完成」。這條在 agent-skills 完全缺席，而無人值守下沒有第二雙眼睛。
4. **成本沒有上界**：AgentFlow 的 `DEFAULT_TIMEOUT_MS=0`（預設無 deadline），由來是 I-050——10 分鐘砍掉 worker，重啟後跑了 54 分鐘才完成 707 測試。連做過這件事的專案都認定 timeout 不可靠而選擇不設。
5. **`.verification/` 證據鏈斷裂**：使用者規則要求證據存檔且任務結束不得刪除。無人值守子程序在多輪 relaunch 後（AgentFlow 上限 2 次）誰負責保存證據沒有定義。

上述 2、3、4 各自都是獨立的專案級工程量。**這是排除 B 的技術理由。**

### Phase 6: 讓機制真的成立（S5.1 review 後追加，2026-09-08）

> **派工操作備忘（2026-09-08 實戰累積，跨 session 適用）**
>
> 1. **agent 自報一律不採信。** 本輪靠獨立複驗抓到 6 次問題，其中 2 次是「agent 說完成、實測完全沒生效」（hard-stop 漏 CLI `next`、漏 `recap`），1 次是 agent **低報**自己的產出（說沒做結構收斂、實際做了）。複驗方式是實跑或 grep，不是讀它的報告。
> 2. **長內容不要用訊息回傳。** agent 回報被截斷 5 次。超過一頁的東西一律叫它寫進 `.verification/<date>/` 再回一句檔名，主對話自己讀。
> 3. **不要同時派兩隻 agent 改同一個檔案。** 本輪犯過一次（兩隻同時改 `plan_runner.py`），收斂正確是運氣不是設計。`plan_runner.py` 幾乎每個 step 都會動到，所以 Phase 6 的 step **一律序列執行**。

## 12. 已裁決事項

本 plan 已獲使用者核准。以下記錄三項已定案的裁決，**不再是待決問題**。

### 裁決 1：採路線 A，路線 B 等 A 跑過一輪真實 plan 再評估

**不是現在評估，也不是永不做。** A 完成並實際推進過一輪真實 plan 之後，用當時的實跑資料回頭判斷 B 值不值得——屆時已知的會比現在多：一輪實際能推幾步、auto-reply 開啟後中斷降低多少、`Confirmed scope:` 有沒有真的擋下範圍蔓延。

B 的缺件清單（§3 的 B1–B9）保持有效。本 plan 完成後 B1／B2／B7／B8／B9 由 A 的產物直接或間接覆蓋，剩下 B3（完成判定）、B4（破壞性操作圍欄）、B6（watchdog）三件需另案處理；B5（成本上界）連 AgentFlow 自己都認定不可靠，需另尋做法。

### 裁決 2：auto-reply 納入，預設 `off`

機制 5（§2.5）**做**。預設值 `off`，缺欄位等同 `off`，開啟是使用者的明示動作。

理由：這個機制的價值不只在「自動開著」，更在於把「什麼算例行」一次界定清楚並寫成程式可判定的形式——這組判定在路線 B 裡會直接變成破壞性操作圍欄（B4）與決策授權（B8）。即使永遠不開啟，這組條件本身就是資產；預設 `off` 讓「不開啟」是零成本的預設路徑。

### 裁決 3：納入機制 6（開跑前四選一確認閘門）

機制 6（§2.6）**做**，並附帶一項預先講死的退路：**若 AC22 顯示作答者能不讀 plan 就挑對，降級為「範圍摘要 + 單純確認」並保留 `Confirmed scope:`，不得靠加難度硬撐**（§6「尚待驗證的假設」）。

這是本 plan 唯一沒有外部前例的機制，也是唯一帶著明文降級條款上線的機制。
