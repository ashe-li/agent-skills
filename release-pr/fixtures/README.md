# release-pr golden set — description 範圍相稱性（scope proportionality）

## 這組 golden set 在測什麼

只測 SKILL.md 的 **Step 3（產生 description）** 這一個 pipeline step，指標對應該 step 的失效模式：**把「查證時才需要」的內容塞進「核准時第一眼看到」的欄位**。

不測分類正確性（那是 Step 2）、不測事實正確性（那是 Step 2.5／4.5 的擋門，已有 fact-checker 覆蓋）。

## 失效模式的來源

`knowledge-base/reports/2026-08-19-alert-description-bloat-audit-and-rewrite-proposal.md` 對 Grafana alert description 做過同一件事的盤點，結論可直接移植：

> 根本問題不是「寫太多」，是**寫錯地方**——retune 史、門檻推導、metric 語義教學都塞進了 `description`。這些是**查證時才需要**的知識，卻被放進**值班時第一眼看到**的欄位。

release PR 的 description 有完全同構的壓力：作者剛做完調查，手上有大量脈絡，而 PR body 是離手前最後一個可以傾倒的地方。**傾倒的動機與讀者的需求無關。**

## 指標

### 主指標（逐段二元判定）— 必要性

對 body 的每一個段落問一句：

> **reviewer 為了決定「要不要核准並部署這次變更」，需要知道這件事嗎？**

- 需要 → 留下（例：這次改了什麼、會不會改變 serving 行為、何時生效、怎麼回滾、部署後看什麼）
- 「出事時 / 查證時才需要」→ **外連，不內嵌**（例：完整證據表、根因推導、機制教學、對其他文件的更正）

判準的鋒利處在於：被外連的內容**不是不重要，而是它的完整版本已經存在別處**（feature PR、KB 報告、runbook）。在 release PR 裡再寫一次只會製造第二個維護點與第二個可能過期的副本。

### 次指標（smell test，非硬上限）— 相稱性

body 字元數應隨改動規模**次線性**成長。既有房規（2026-09-06 實測，`gh pr view <n> --json body,files`）：

| PR | 檔案 | +/− | body 字元 | 每檔字元 |
|---|---:|---|---:|---:|
| #7969 | 64 | +3353 / −697 | 7897 | **123** |
| #8117 | 8 | +1232 / −50 | 3108 | 389 |
| #8121 | 3 | +420 / −2 | 2658 | 886 |
| #8124（修正後）| 1 | +23 / −7 | 1053 | 1053 |

**「每檔字元」顯著高於同規模鄰居就要停下來問主指標。** 這只是聞味道，不是門檻——單檔但語義極重的變更（feature flag、schema migration、安全修補）可以合理偏高。

### 反指標（避免過度修剪）

**「越短越好」是錯的。** #7969 的 7897 字元完全正當：64 個檔案、跨多個 feature，reviewer 沒有那些說明無法核准。修剪的對象是**與這次核准決策無關的內容**，不是長度本身。

任何把 fixture 02 / 03 判成「應該大幅縮短」的實作都是**過度修剪**，等同於失敗。

## 跑法

這是**判讀型 golden set**，不是可執行測試：拿 fixture 的 `input` 段當 Step 3 的輸入條件，產出 body 後對照 `expected_*` 逐條檢查，結果記進 `acceptance_results.md`。
